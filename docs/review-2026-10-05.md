Replica: open issues
====================

Left over from the 2026-10-05 review (full text in review-2026-10-05-old.md).
Most of that review was fixed on 2026-10-07. This is what's left.


Needs a decision
----------------

* Deleted-then-recreated files. If you have change: source <-> dest with no
  delete edge, and you delete a file at source, the engine records a
  tombstone for it. If you later create a file with the same name at source,
  the engine thinks it's a newcomer and copies the old dest version over it.
  This is how the README says it works, but it's surprising. Question is
  whether a tombstone should mean "this side deleted it" (so a new file is
  an edit and wins) or "this side doesn't know about it" (current).

* Ref ids aren't stable. A ref under a multi-endpoint label gets
  "?root=/path" in its id; a ref under a single-endpoint label doesn't. So
  if you add a second folder to a label, the first folder's ref gets a new
  id and loses its records. Same if you remove one. Also, if you point a
  single-endpoint label at a different folder, the old folder's records get
  applied to the new one. Probably needs a table mapping ref -> root that's
  checked at the start of each cycle.

* Gate/pause state is lost on restart. Closing the gate from the dashboard
  doesn't survive a restart, and you need to restart to pick up config
  changes. Should be stored in the setting table. Need to decide what
  happens when the stored state and gate: in the config disagree. Probably
  "closed if either says closed".

* Permissions on overwrite. New files get the donor's mode. Overwrites keep
  the destination's existing mode (same as cp). That means a chmod on one
  side never propagates. Could go either way.

* Narrowing the pattern deletes records. If a file no longer matches the
  pattern, its records are deleted, so if you widen the pattern again later
  the file starts from scratch (identical content aligns, different content
  conflicts). This is safe but it means temporarily narrowing the pattern
  throws away the baseline. The other option is to keep the rows and just
  skip them.

* Unreadable peers. If dest can't be read (e.g. the path is now a
  directory), an edit at source is held rather than recorded as done, so
  it's still pending when dest comes back. But a delete at source will
  still go to a third replica if the delete edge doesn't pass through dest.
  Not sure that's right.

* Dashboard cost. When no cycle is running, every page load and status poll
  walks all the roots again, under the engine lock. While a cycle is running
  it serves the snapshot from the end of the last cycle. Could just always
  serve the snapshot; then gate/pause changes wouldn't show until the next
  cycle.


Bugs
----

* decide() can use a file as a donor in the same plan that overwrites it.
  With a -> b; b -> c and edits on both a and b, c ends up with b's old
  content. Needs to evaluate in dependency order.

* The config loader accepts things that don't work:
  - propagate with change but no create: new files are never copied.
  - a propagate block in an entry replaces the whole default block, so one
    overridden key drops all the inherited edges.
  - pattern on a template relation matches the hole values, not the path,
    so "*.md" matches nothing.
  - a typo like {nmae} in a path becomes a literal file name.

* A wrong value type under entries._ (e.g. pattern: 5) is reported against
  whichever entry inherits it first, not against _.

* Globs are case-sensitive even on case-insensitive filesystems. No exclude
  list (.DS_Store gets synced). scan: picks up .git and node_modules.

* Conflict messages show raw ref ids ("a vs dest?project=x") and don't say
  what each side changed or that a conflict: rule would fix it.

* .warn text in the light theme is yellow on white, 1.96:1 contrast.

* History page: no filter, and the "put it back at this path" advice
  doesn't figure out which side is upstream, so in a one-way relation the
  restored file gets reverted.


Minor
-----

* /status.json "errors" is a count since the process started.
* The "cycle N done" log line is only printed when something happened.
* Cargo.toml still says 1.0.0 even though the config format changed
  (two-item lists are now two endpoints; relative paths, interval: 0, and
  rename without pattern are rejected). No migration note anywhere.
* docs/design-style.md doesn't match style.css and isn't in git, but the
  README links to it.
* Code cleanup: the intent journal uses ref ids but logs use display names;
  parse_size and parse_duration are two separate parsers that disagree on
  details; hashes are BLOB in record but hex in archive; label.rs has three
  types for one endpoint; Engine.archive and Engine.reserved are set from
  outside instead of passed to the constructor; skip reasons, archive
  reasons and intents are strings; render_page is one huge function; donor
  files and archive copies are read whole into memory.
